# Agent handoff: build the whole loop

## Outcome

Build a product-led, interactive frontend in which rich objects are created or revised locally, not merely downloaded and dropped into a generic landing page. The target is ambitious scroll choreography and responsive props with deliberate composition, materials and legible information. The user values 3D/2.5D/2D and physically distinct glass/material families, but not gratuitous complexity.

## Work in this order

1. **Inspect the target.** Read its existing brand tokens, product intent and integration constraints. Determine whether this is a new page or an existing product surface. Do not replace established ownership with a new design system.
2. **Choose the medium.** Compare live 3D with one simpler alternative. State why the chosen interaction needs that medium. Choose a single clock/controller and a separate semantic DOM baseline.
3. **Probe local capability.** Run the read-only doctor, record Blender/browser/backend versions and establish a small resource lease. Do not launch a render swarm alongside the operator's foreground workload.
4. **Create the source.** Use a deterministic recipe or a rights-cleared source asset. For the included exercise, improve the trainer's silhouette/collar/intersections from three fixed views before increasing visual complexity. Do not claim it is a product scan.
5. **Look development.** Lock the camera/exposure and compare material/lighting alternatives. Preserve the native project, dependent inputs and material assumptions. Bake any procedural shading needed by the browser.
6. **Export.** Produce a named-part GLB, source/rights manifest, poster and lower-detail path. Use the actual Khronos validator when available, then independent import and actual-browser inspection.
7. **Build interaction.** Implement silhouette → construction → finish beats. Every motion teaches something. Keep user orbit and manual state separate from scroll; support reverse/seek/resize, direct buttons and keyboard.
8. **Validate and refine.** Inspect actual desktop/mobile frames, run semantic assertions and measure the target environment. Repair visible defects; repeat against the same camera/progress checkpoints.
9. **Return the deliverable.** Provide runnable source, source/asset paths, measured results, remaining limitations and exact next local commands. Integrate with the existing evidence system, not a competing registry.

## Required outputs for a real task

A short accepted brief and medium decision; editable `.blend` or equivalent plus generator; version/input/rights manifest; validated GLB and poster; application integration; screenshot/contact-sheet evidence; keyboard/touch/reduced-motion/fallback results; performance observations with device/browser context.

Use PASS / FAIL / BLOCKED_ENV / NOT_RUN per lane. Production-quality is an acceptance result, not a filename or marketing adjective. Do not announce completion because the package installed, a renderer created a context, or the code compiled.

## Selected skills to start

`fd3d-art-direction`, `fd3d-medium-selection`, `fd3d-blender-autonomy`, `fd3d-procedural-products`, `fd3d-gltf-delivery`, `fd3d-scroll-story`, `fd3d-interactive-props`, `fd3d-visual-qa`.

Load other skills only when the task reaches their concern. The upstream Anthropic skill is available for a separate critique pass, not loaded automatically or installed by the sync script.

## Challenge the recommendation

Maybe live 3D is not what makes the reference compelling; test the same composition with a poster. Maybe the asset, not the framework, is the quality bottleneck; compare a clay render before migrating engines. Maybe motion is technically smooth but narratively empty; state the information each beat reveals. Maybe procedural geometry is more editable than image-to-3D; compare cleanup time rather than first-output novelty.
