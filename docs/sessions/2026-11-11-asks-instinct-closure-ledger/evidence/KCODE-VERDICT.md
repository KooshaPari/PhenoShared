## 5. Is 196 correct?

**Correct as a dedupe result; wrong as an operator-ask count, in both directions.**

**Understates volume by ~13–15x.** 2,529–2,934 operator messages collapsed to 196 rows.
Operator repetition is signal (the AGENTS.md asks-coverage rule explicitly says one-word nudges
like `go` and `.` are real prompts and should be counted, not dropped). Here the highest-frequency
real asks are `test` x108, `first` x72, `do this ordinary coding task` x63, and
`turn N xxx…` x57 — all **test fixtures** that dedupe hides but volume exposes.

**Overstates "operator" distinctness.** Of the 196 rows, ~76 are provably not operator-authored:

* product/system prompts — `You are generating personalized feature tips for a developer assistant
  called Kiro Crew`, `You are generating contextual prompt suggestions…`, `You are a memory
  consolidation agent`, `You are a session naming agent`, `Reassess the user's request using its
  full context…` (safety judge)
* automation — `[auto] …`, `🐝 **Swarm await finished**`, `DM from owl: …`, `Create this
  session's concise status car…`
* fixtures — `test`, `first`, `seed session for resume test`, `do this ordinary coding task`,
  `turn N xxxx…`

Leaving **~120 human-authored rows, of which ~57 are substantive (≥80 chars)**. Several of the 120
are dispatcher-written subagent briefs (`TASK: …`, `READ-ONLY …`, `RESEARCH-ONLY TASK …`) rather
than operator chat turns.

## Why `.kcode` is genuinely smaller than `.jcode`

No hidden store — the fork was used sparingly. `kcode` has 1,253 canonical sessions totalling
31 MB, of which ~9 MB is `.bak` duplication; `.jcode` is 2.80 GB over 12,770 files, a ~90x gap.
Extrapolating `.kcode`'s 2.02 operator messages per session to `.jcode`'s 12,770 files implies
**tens of thousands** there, consistent with the stated expectation. The asymmetry is usage
volume, not extraction.

Additionally: 721/1,253 sessions have a prompt, but only **85 distinct titles** exist across 790
title slots — deep fork chains (`parent_id`, `fork_depth`) copy parent `messages[]` into children.
`session_sauropod` and `session_owl` are the same conversation forked; sauropod's 1,134 messages
are a superset. Any dedupe must key on text, not on file or session id.

## Recommended miner fix

1. Keep the current key (it is correct): `messages[].role=="user"` → `content[].type=="text"`,
   drop blocks containing `<system-reminder>`.
2. **Do not** globally collapse by `text_sha256` for coverage purposes. Emit every occurrence with
   a `dedup_group` column so both volume and distinctness are available. If dedupe is required,
   scope it to within-session and keep a `occurrences` count.
3. Add a `synthetic` classifier for the prefixes above; the current `substantive` flag alone
   passes KiroCrew product prompts as operator asks.
4. Add `is_debug` / `is_canary` to each row so test fixtures (`test` x108) are separable.
5. Scan `.json` only for canonical counts; treat `.bak` / `.journal.jsonl` as a separate
   `source_variant` so 2,529 and 2,934 are not conflated.
