## Security: credential exposed on a public repo

`ops/caddy/Caddyfile.helioslite` is present on the **public default branch** of
`zz-ref-HeliosLite` (formerly `HeliosLite`), introduced in commit `9d67435d0`.
It contains a bcrypt password hash for Caddy basic auth.

A bcrypt hash is not plaintext, but it is publicly readable and therefore
crackable offline at leisure. The `$2a$14$` cost factor makes a brute-force
attack expensive but not impossible, and any password reused elsewhere is at
risk. **The password behind it should be rotated.**

A content scan across all refs found nothing else: zero hits for AWS access
keys, `sk-` keys, GitHub tokens and PATs, Slack tokens, PEM private keys,
Tailscale auth keys and MagicDNS names, Google, npm, HuggingFace, GitLab, CGNAT
addresses. Of 34 risk-named blobs, 33 were scanned and all were inert test
fixtures or templates.

This is the second time a real credential has been found in this consolidation,
after the `canvasApp` OpenAI keys. Both were found by scanning, not by review.

## Resolved: the HeliosLite size question

Two figures appeared to contradict each other: a branch reported to hold 2.52 GiB,
and a full `--all` bundle of only 96 MB that still round-tripped every ref.

Measured offline against a bare mirror, both are correct and they measure
different things:

| Tree | Files | Blob bytes | Largest blob |
|---|---:|---:|---:|
| `main` | 1,560 | 19,911,951 (0.02 GiB) | 862,285 |
| `absorb/no-remote/forge-20260715` | 20,646 | 2,700,563,365 (2.52 GiB) | 1,557,648 |
| **whole mirror, packed** | 80,702 objects | **100,426 KiB (98.07 MiB)** | |

The 2.52 GiB is uncompressed blob content. The entire repository packs to
98.07 MiB, because the payload is ~10,463 conversation snapshots and a model
cache that are highly repetitive. A 96 MB bundle therefore contains everything -
the compression ratio is roughly 26:1, not a missing branch.

The bundle's completeness proof stands: the round trip re-cloned it and compared
all 1,061 ref names and shas, and a clone fails outright if an object is missing.

Worth recording anyway: the default branch is 0.02 GiB of the 2.52 GiB, so a
heads-only or `main`-only capture would have looked reasonable and dropped 99% of
the content mass. That is the argument for `--all` and for counting refs rather
than eyeballing size.

## Resolved: the HeliosCLI "ref mismatch" was a bug in the checker

Preservation pushed HeliosCLI's refs and then reported
`ref mismatch: 0 missing, 0 differing`. That message is self-contradictory -
zero missing and zero differing can only mean the registry holds *extras*.

Measured directly, source and registry agree exactly:

| | Refs | Namespaces |
|---|---:|---|
| `zz-ref-HeliosCLI` source | 1,340 | heads 18, tags 851, pull 471 |
| `refs/preserved/zz-ref-HeliosCLI/` | 1,340 | same |

Zero missing, zero extras, zero shas differing. **The preservation was correct all
along.**

The fault was in `preserve_refs.source_refs()`, which still filtered the expected
set to `refs/heads/` and `refs/tags/`. After the push was widened to the whole
ref graph, the expectation held 869 refs while the registry held 1,340, so 471
legitimate refs appeared as unexplained extras and a complete push was reported as
a failure. The filter is removed and the expectation now covers every namespace.

This is the third time in this consolidation that a verification step was wrong
while the thing it checked was fine, after the `heads/main` key mismatch and the
`HEAD^{tree}` self-comparison. Verification code deserves the same suspicion as
the work it checks.

## Audit: two absorption manifests record a rename as a migration

`audits/absorption-justifications/` holds 19 machine-generated manifests, each
carrying a confidence grade. Checking them turned up a class of false assurance.

**Two manifests absorb a repository into itself**, both graded HIGH confidence,
with receiving path `n/a` and bundle `none`:

| Manifest | Source | Target | Same repo id |
|---|---|---|---|
| `helios-cli-2026-07-17.md` | `helios-cli` | `helios-cli` | 1165315873 |
| `heliosCLI-2026-07-17.md` | `heliosCLI` | `helios-cli` | 1165315873 |

They point in opposite directions and describe a rename chain
(`heliosCLI` -> `helios-cli` -> `zz-ref-HeliosCLI`) that was recorded as though each
step moved content. Neither moved anything.

The instructive part is how easily this hides. A name comparison finds only the
first one. `heliosCLI` and `helios-cli` differ by a hyphen, so the second looks
like a legitimate move until you resolve both through the API and compare
repository ids. That is the same mistake as the earlier `zz-ref-*` false
duplicate, and the same fix: **compare ids, never names.**

A completeness rubric cannot catch this either. Every section of the manifest is
"backed by a verified artifact" because the artifacts all describe the source
itself. Both files now carry a correction notice, and any future generator should
assert `source_id != target_id` before grading anything.
