# The restorer: identified by behaviour, not by actor

Date: 2026-11-17

## What was ruled out

| Hypothesis | Result |
|---|---|
| Org audit log names the actor | `gh api orgs/KooshaPari/audit-log` returns 404 — enterprise-only |
| A scheduled task does it | `JcodeClosureHourly` and `JcodeClosureDailyDeep` exist, but they run `run-hourly.cmd` / `run-deep.cmd` at :12 past the hour; the repo timestamps are 09:11, 11:34, 13:29–13:34 — no alignment |
| `repo-audit-run.ps1` creates repos | No. Its own header: "Read-only. No commit, push, checkout, stash, reset, clean, or state-changing fetch was run" |
| A persistent script is running | `findstr` over `Agents/closure`, `Agents/*.ps1`, `PhenoShared/scripts` finds no `gh repo create`, no `audit/snapshot-`, no "Snapshot import of" emitter |
| A running process shows it | `wmic process` command lines contain no `snapshot`, `repo create`, or `audit` |

The actor acts inline from an agent session, so nothing survives the command.

## What the behaviour shows

The recreation is not arbitrary. Every restored repository's live tip equals its
preserved tip:

| Repository | Live `main` | Preserved |
|---|---|---|
| `harness-ops` | `bb4ac29853` | `bb4ac29853` |
| `dagrun` | `8080d73a` | `8080d73a` |
| `phenotype-canonicalization` | `570e2c73af` | `570e2c73af` |

And the timing is exact. `phenotype-canonicalization` was deleted at
**2026-11-16 08:03** and the API now reports `created 2026-11-16T09:11:15Z` —
recreated **68 minutes later**, at the identical committed tree.

So the restorer rebuilds from `refs/preserved/`. It is not an accident and not a
third party: it is the preservation mechanism being replayed as a restore.

## Why this matters more than the actor's name

Preservation and consolidation were in direct conflict and nobody had noticed:

- preserving a namespace makes deletion **safe**, because history survives;
- restoring from that namespace makes deletion **pointless**, because the
  repository comes back.

Deleting 100 repositories while a restore loop runs would produce 100
recreations. That is why the estate went 86 → 118 while 1 repository was deleted.

## The fix: tombstones

`docs/absorption-ledger/tombstones.txt` records repositories deleted on purpose.
`scripts/restore_preserved.py` now refuses `--create` for a tombstoned repository
and says so, while keeping `--force` for a deliberate recovery:

```
$ python scripts/restore_preserved.py phenotype-canonicalization --create
phenotype-canonicalization is tombstoned: it was deleted deliberately, and
restoring it would undo that.
Its history is still in refs/preserved/phenotype-canonicalization/ and can be
rebuilt with --force.
```

`--list` marks tombstoned namespaces so the state is visible without querying.

This keeps both properties at once: history stays recoverable, and a deleted
repository stays deleted. It only works if whatever runs the restore honours the
file — which is why the finding above matters. If the restore is being driven by
an agent session rather than this script, the tombstone has to be respected
there too.

## Early warning

`scripts/watch_estate.py` snapshots the repository list to
`estate-snapshot.json` and diffs against it, reporting additions, removals and
size changes with the window in which they happened. Run it on a schedule and the
next burst is attributable to an interval even when the actor is not.

Baseline recorded 2026-11-17: **118 repositories**.
