# v0.11 Harbor Install Audit (WBS task C1)

**Date:** 2026-08-09
**Status:** INVESTIGATION COMPLETE — root cause identified, fix recipe
drafted. Execution blocked on user push auth for site-packages cleanup
(per AGENTS.md §10.4 — modifying system Python site-packages is
host-side state).

## TL;DR

The `harbor-0.0.0.dev0.dist-info` is a **stale dist-info from a prior
failed install** at `/opt/homebrew/lib/python3.14/site-packages/`. The
referenced `harbor/__init__.py` does NOT exist in the same directory —
the package code was removed (or never installed) but pip left the
dist-info behind.

This stale entry does NOT block the current `harbor 0.1.42` install
at `/opt/homebrew/Caskroom/miniforge/base/lib/python3.13/site-packages/`,
because each Python install has its own site-packages. But it pollutes
`/opt/homebrew/lib/python3.14/site-packages/` and can confuse tooling
that introspects all Python site-packages.

## Findings

| Path | Status | Notes |
|------|--------|-------|
| `pheno-harness/harbor/` (local) | **namespace package** | Contains 4 PowerShell scripts only; no `__init__.py` |
| `portage/src/harbor/` (real harbor source) | OK | Editable-installed from portage at 0.1.42 |
| `/opt/homebrew/Caskroom/miniforge/base/lib/python3.13/site-packages/harbor/` | OK | harbor 0.1.42 installed |
| `/opt/homebrew/lib/python3.14/site-packages/harbor-0.0.0.dev0.dist-info/` | **STALE** | METADATA only has `Name: harbor`, `Version: 0.0.0.dev0`; `harbor/__init__.py` missing |

### `pheno-harness/harbor/` is a local namespace package shell

The `pheno-harness/harbor/` directory exists to hold the 4 PowerShell
CLI callers (`run_agent_eval.ps1`, `run_tbench_local.ps1`,
`run_tbench_models.ps1`, `run_tbench_routes.ps1`). It has no
`__init__.py`, so Python treats it as a namespace package.

This shadows the real `harbor` package when Python is launched from
the pheno-harness cwd:

```python
>>> import sys; sys.path[0:3]
['', '/Users/<REDACTED>/lib', ...]
>>> import harbor
>>> harbor.__file__  # namespace package, no __file__
>>> harbor.__version__
AttributeError: module 'harbor' has no attribute '__version__'
```

In a venv where the cwd is pheno-harness, `import harbor` resolves to
the local namespace shell. To get the real harbor, you need to chdir
to portage or run from outside pheno-harness.

### `harbor-0.0.0.dev0.dist-info` is stale

The dist-info at `/opt/homebrew/lib/python3.14/site-packages/` was
left behind by an old `pip install -e` (or partial uninstall). Its
content:

```
METADATA:
  Metadata-Version: 2.1
  Name: harbor
  Version: 0.0.0.dev0

RECORD:
  harbor/__init__.py,,

top_level.txt:
  harbor
```

But `/opt/homebrew/lib/python3.14/site-packages/harbor/` does NOT
exist. The dist-info is orphaned.

## Root cause

The stale dist-info came from a prior botched pip operation against
`/opt/homebrew/bin/python3.14`. It is benign for current operation
but pollutes introspection. Most likely cause: a prior `uv pip install`
of an editable harbor source that was later moved/deleted without a
matching `pip uninstall`.

## Recommended fix (v0.11 task C2)

1. **Remove the stale dist-info** (host-side state, gated on user
   push auth):

   ```sh
   rm -rf /opt/homebrew/lib/python3.14/site-packages/harbor-0.0.0.dev0.dist-info
   ```

2. **Rename `pheno-harness/harbor/` → `pheno-harness/harbor_cli/`**
   to eliminate the namespace shadow. The PowerShell wrappers are
   referenced from `harbor/` symlinks + `harbor.run_agent_eval` CLI
   entry; renaming requires updating 4 call sites.

3. **Verify**: `pip check` should show no broken installs; `import
   harbor` from pheno-harness cwd should resolve to the real harbor
   0.1.42 package.
