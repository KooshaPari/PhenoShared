# Human intent and the engineering interpretation

This file is synthesis, not a transcript. INT-001 is the controlling scope request and INT-002 requests the artifact. The user wants an explanatory codebase atlas, independently measured assurance, aggressive maintenance reduction, finer-grained product specifications, and honest competitive proof across the retained portfolio. They explicitly prefer reusable dependencies and maintainable patch/adaptation strategies over complete handrolling.

The execution capacity is ten interactive Tracera seats plus up to two seats for every other project-level repository. That is a capacity assumption, not an instruction to run every build or GPU job simultaneously. Foundations and dependency maintenance are pooled. Product work must not wait for Tracera to finish.

The user proposes further absorption of Localbase/RIPFitnessApp into PhenoApps and several foundation homes into Pheno. This package remembers those candidates but neither performs nor independently authorizes any migration, rename, deletion, or publication. Package boundaries and consumer contracts survive repository movement.

The intended completeness is accountability for every relevant artifact and meaningful semantic unit, including non-code material. It is not a demand for prose beside every syntax token. Hundreds or thousands of genuine entities are expected where the product warrants them; arbitrary per-type quotas would create another maintenance burden.

## Binding prior constraints carried forward

- Tracera is the persistent canonical product/system model with bounded navigation and dissatisfaction detection; audit/workflow records are supporting views.
- AgilePlus and PhenoDocs are reusable tools, not homes for hardcoded cross-product operational truth. Preserve better repo-local intent/scrape systems and actual engine contracts.
- Independent unit, integration and E2E coverage floors are at least 85% in required profiles; stronger accepted floors remain. Critical obligations require complete satisfaction. Passing is not a percentage-of-failures allowance.
- CVP means a viable, useful, polished, installed version of the accepted current horizon. It does not authorize silently dropping unfinished promised capabilities to claim an MVP.
- Product evidence is captured from real artifacts in controlled environments. Authored branding/concept art is not proof of implemented UI behavior.
- No credential bypass, destructive cleanup, admin merge, invented approval, fake pass, or automatic lifecycle transition from a repo prefix/topic.
