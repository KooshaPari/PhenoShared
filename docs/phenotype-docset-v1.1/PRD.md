# Product requirements: an explainable, verifiable portfolio

## Problem

The portfolio has accumulated more implementation, work sessions and documentation than an operator can reliably comprehend. Repositories have moved and been renamed; code can exist in several homes; old summaries may contradict actual current products; verification tools can return success without measuring the advertised property. A lower repository count alone does not repair those problems.

The current program must expose why each meaningful artifact exists, what semantics matter, what is missing or unnecessarily expensive, and whether changes actually improve a usable product. The goal is reduced maintenance burden and trustworthy current viable products, not maximal code generation, test count, documentation volume or GitHub activity.

## Users and jobs

The owner needs a reliable macro view, a real installed application to evaluate, and a clear explanation of what scarce attention should address next. Product agents need bounded context, precise contracts and discoverable dependencies without treating every unrelated file as required context. Assurance agents need independent oracles, reproducible environments and a truthful failure model. Future maintainers and external users need clean installs, documented interfaces and portable evidence, not private chat history.

## Primary journeys

A product owner selects a capability, reads its intent, follows it to real entrypoints and dependencies, sees supported profiles and evidence, and identifies gaps. An assurance agent starts from the accepted contract, injects a meaningful failure and proves the gate catches it. A simplification owner identifies custom glue, compares a maintained dependency, preserves required behavior and publishes the same useful product with less maintenance. An operator installs the resulting artifact outside the repository and supplies feedback from actual use. Tracera ingests the same records later without forcing existing projects to migrate their authoritative databases.

## Scope

The provisional allocation has 23 product/lab candidates, four pooled foundation homes and three supporting surfaces, plus PhenoApps and the Agentora capability as conditional additional records. Ten seats focus on distinct Tracera workstreams; other product pairs split implementation and independent assurance. Session capacity is not execution concurrency. Native/GPU/build/review resources have independent admission.

The contemplated final absorptions into Pheno/PhenoApps are contextual. This package does not execute them. Their component and source IDs should be retained so the atlas survives moves, and their consumers should not wait for an unnecessary ecosystem-wide consolidation.

## Required outcomes

Each material artifact is classified and its meaningful semantic units link to a reason, constraints, consumers and evidence status. Unknown rationale is visible rather than invented. Specifications cover happy paths, failure, recovery, data, interfaces, UX, resources, security and operations at the product's genuine granularity. The QA matrix tracks independent coverage and execution by profile. Dissatisfaction records support changes that preserve accepted semantics. Comparative pilots test practical usefulness and maintenance as well as speed. A current-horizon artifact is installed, exercised, documented and traceable to its source.

## Success measures

Measure accepted capabilities reaching verified/released/adopted states; time from bounded horizon to installed product; defects first discovered only after installation; rationale/verification blind spots removed; stale-evidence exposure; custom subsystems removed with parity; patch maintenance cost; consumer migration failures; and real operator interventions. Report the magnitude and denominator. Do not compress these into a single number that allows visual polish to offset data loss.

## Non-goals

No claim of universal superiority over all software; no requirement that every tiny module become an app/service/repo; no universal database; no forced monorepo; no one-paragraph-per-source-line exercise; no invented thousand-FR quotas; no reconstruction of missing exact prompts; no simultaneous re-audit of unchanged repos; and no current-game engine winner selected from marketing or empty scenes.

## Current viable product

Freeze the accepted current horizon and make it coherent, useful, durable, polished and distributable. A witness journey exercises a central path but does not erase the remaining accepted obligations. An explicit scope decision is required to move a promise out of the current horizon. For libraries, use real consumers. For labs, use a reproducible experiment. For a historical reference, use custody and truthful status rather than a fabricated release.

## Revision 1.1 — ecosystem-wide consumer impact

[Continuous ecosystem-first evolution](architecture/ECOSYSTEM-FIRST-EVOLUTION.md) applies to design, implementation, verification and delivery. External and owned reuse are both considered before handrolling. Current and committed consumers determine compatible behavior; plausible future consumers guide inexpensive seams, not speculative mandatory dependencies. Capability owners, adapters, consumer versions, cross-repo rollout and aggregate maintenance effects belong in each material change record. The repository write boundary does not narrow reasoning or expand authority. The proposed impact shape is `schemas/ecosystem-impact.schema.json`; it is structural evidence, not an approval or proof of parity.
